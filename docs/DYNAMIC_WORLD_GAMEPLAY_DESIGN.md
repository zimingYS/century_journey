# 动态世界与生存玩法设计草案

> 状态：概念设计，尚未接入实现。
>
> 本文汇总《世纪之旅》动态世界、生态、生存、体素表现与相关玩法的长期设计方向。
> 它描述目标、约束、数据归属、实施策略与风险，不应被视为当前已经可用的功能清单。

## 1. 目标与边界

《世纪之旅》的世界不应只是由种子生成后永久静止的背景。目标是让气候、水、土壤、植被、动物和玩家活动产生缓慢、可理解、可恢复的因果关系：玩家能观察环境、适应环境，也能通过建造、农业、治理和技术改变局部环境。

动态世界的重点是可信与可玩，而不是追求完整的气象学、流体力学或生态学模拟。任何系统都必须同时满足以下条件：

- 结果可由世界种子、固定步时钟和持久化状态重现。
- 远方世界使用低成本摘要，只有玩家附近才展开为精细模拟。
- 环境变化有清楚的视觉、声音或工具反馈，不能让玩家觉得随机受罚。
- 玩家建筑、存档兼容与单机性能优先于环境模拟的真实性。
- Game 持有权威规则，Client 只表现结果；表现帧率不能改变游戏规则。

本文不要求一次实现所有机制。动态世界应通过可独立验证的纵切面逐步扩展。

## 2. 当前项目基础与事实

当前项目已经拥有可供后续系统复用的基础，但本文大部分内容尚未实现：

- 世界使用种子、区块流送和 `16 x 16 x 16` 的 `ChunkData` 体素数组。
- 游戏规则在 `FixedUpdate` 中运行；世界时钟为 20 Hz，已提供游戏分钟、小时、日、节气、季节和年份消息。
- 气候采样器已经能以世界坐标生成基础温度、基础湿度，并提供季节修正后的环境采样。
- 生物群系定义当前包含地形参数、表层方块、树密度和矿物配置。
- 树目前是地形生成后的静态结构：结构生成器在适宜地表上放置简单树干和树冠。
- 方块定义已经预留 `light_emission`、`light_transmission`、模型、状态、重力等字段，但这些能力尚未完整接入运行时。
- Client 当前使用后台贪心网格任务和 Bevy 标准材质渲染区块；水拥有独立网格通道。

实现新功能时必须保留“基础生成不随实时季节反复改变”的约束。旧世界的地貌、地下结构和基础气候由种子与生成版本决定；动态模拟只在其上叠加可持久化的变化。

## 3. 总体世界模型

世界应分为四类信息，而不是把所有信息塞入一个“生物群系”标签：

```text
地貌层：平原、山地、海岸、盆地、地下洞穴
气候层：基础温度、降水潜力、主风带、季节、天气
土地覆盖层：草地、灌木、稀疏林、森林、裸地、沙地、湿地
生态区层：由地貌、气候和土地覆盖组合得到的玩家可见区域名称
```

例如，玩家种植大量树木后，不应重写“平原”本身的高度、地下矿物和河道；它应从“温带草原”逐步变成“温带森林平原”。同样，砍伐干旱地区的树木不会立刻把平原变成沙漠，而应经历草地退化、灌木地、半荒漠、裸地和沙化等长期过程。

```text
基础地貌 + 基础气候        由世界种子稳定生成
天气、植被、土壤、扰动      由世界模拟缓慢改变
生态区名称与表现            从上述状态派生并缓存
```

## 4. 数据归属与运行层级

遵守项目的依赖方向：`Shared <- Engine/Content <- Game <- Client/App`。

| 层级 | 职责 | 不应承担的职责 |
| --- | --- | --- |
| Content | 树种、方块、作物、天气规则、材料和生态阈值定义 | 玩家状态、实时区块所有权 |
| Game | 权威时钟、环境状态、方块变更、玩家生存、生态结算、存档语义 | 网格、粒子、云层、音效表现 |
| Client | 地形材质、天气、树叶摆动、水面、UI、视觉与声音反馈 | 决定树是否生长、玩家是否受伤 |
| Engine | 资产解析、后台任务、原子持久化和诊断 | 具体生态或生存规则 |
| Shared | 稳定 ID、时钟类型、跨层值类型 | 运行时世界所有权 |

权威环境规则进入 `FixedUpdate`。建议在现有 `SimulationSet::Clock` 后新增或明确生态、流体、环境暴露等集合，使依赖顺序可读：

```text
Clock
-> Climate / Ecology / Fluids
-> Commands / Interaction
-> Player Exposure / Survival
-> Entities
```

实际排序可随实现调整，但任何系统都必须明确其时间源、前置数据和副作用。

## 5. 分层空间与性能策略

大地图不能把每棵树、每格水、每团云都作为持续更新的对象。世界按距离和重要性使用不同精度：

```text
远方：种子函数与粗粒度摘要
中距离：生态区块、流域、稳定候选位点
近距离：具体树、活跃水格、实体和方块改变
表现：每帧生成云、雨、波纹、树叶摆动和音效
```

推荐尺度如下，具体尺寸需要以性能基线测量后调整：

| 模型 | 建议范围 | 更新频率 | 内容 |
| --- | --- | --- | --- |
| ClimateCell | 256 至 512 方块 | 游戏小时或更慢 | 温度、湿度、气压、云水、主风向 |
| HydrologyPatch | 128 至 256 方块 | 游戏日或天气事件 | 地下水、河流流量、积雪、蓄水 |
| EcologyPatch | 64 至 128 方块 | 游戏日、节气或季节 | 树冠、土壤、种子库、扰动、土地覆盖 |
| Chunk | 16 方块 | 按需、固定步预算 | 体素、水格、光照、局部实体 |
| Client 表现 | 可视区域 | 渲染帧 | 云、雨、雾、风、粒子、动画 |

以 `5000 x 5000` 的地表为例，不能实例化数百万树。使用 `64 x 64` 生态区块时，理论上约有 6200 个区块；它们仍应按需生成，世界种子可重建未修改区域。持久化规模应主要与玩家影响范围有关，而不是与地图面积线性绑定。

## 6. 世界生成、气候与动态生态区

### 6.1 基础生成

基础生成应稳定地输出：

- 高度、坡度、地质、海平面、地下洞穴和矿物背景。
- 基础温度、基础湿度、基础降水潜力、主风向和流域方向。
- 初始地貌与初始土地覆盖。
- 稳定的候选树位点、动物位点、遗迹位点和资源位点。

这些结果只受世界种子与生成版本影响。修改算法时必须提高生成版本，旧世界继续使用其创建时的版本。

### 6.2 动态生态区

动态生态区不是直接改写基础生物群系，而是根据粗粒度状态计算派生分类：

```text
地貌 = 平原
基础气候 = 温带偏湿
树冠覆盖 = 高
土壤水分 = 中高
土地覆盖 = 森林
玩家可见生态区 = 温带森林平原
```

分类必须带有空间平滑和时间滞后。示例：树冠连续多个季节高于 60% 才进入森林；连续多个季节低于 40% 才退出森林。这样单次砍树或单次种植不会导致地图标签抖动。

### 6.3 气候与天气

天气使用简化天气单元，而不是完整大气流体：

```text
WeatherCell
├─ air_temperature
├─ air_humidity
├─ pressure
├─ cloud_water
├─ wind_direction
├─ wind_speed
└─ precipitation_intensity
```

建议模型：

```text
当前温度 = 基础纬度温度 - 海拔降温 + 季节偏移 + 昼夜变化 - 云层遮蔽
风力 = 主风带 + 季节风 + 邻近气压差 + 地形偏转
降水 = 湿气输送 + 饱和/冷却 + 山地抬升
```

山脉可造成迎风坡降雨与背风坡雨影，从而自然形成湿润森林、草地和干旱区域。天气变化要缓慢移动、可预报，并给玩家提供天空、风声、云层、气压或工具提示。

## 7. 水文与水体系统

水同时是地貌、环境储量、局部体素流体和玩家资源。应分层处理：

```text
种子水文骨架：海洋、河流、湖泊、流域、泉眼
生态水分：降水、土壤水、地下水、积雪、蒸发、径流
局部水体：玩家附近的水位、流向、取水、蓄水与渗透
玩家交互：饮水、游泳、湿润、体温、呼吸与水流推力
```

### 7.1 水量与均衡

局部水应是有限水量，而不是无限复制水源。每个活跃水格保存量，例如 `0..255`：

```text
0       无水
1..31   薄水膜，转化为地面湿润、渗透或蒸发
32..255 可见水面，水面高度由水量决定
255     满格水
```

水的局部结算顺序：

```text
向下流动
-> 与较低邻格横向均衡
-> 越过容器边缘时溢流
-> 对可渗透地表执行渗透
-> 对暴露水面执行蒸发
-> 激活受影响邻格
```

围墙、坑洼和地形自然产生蓄水，不需要在放水时先全图搜索“容器”。水量过低时不能凭空消失：土壤、沙地可吸收为 `soil_moisture`；高温强风下可蒸发；开放边界可流向下游。

### 7.2 水源与水质

| 水源 | 规则 |
| --- | --- |
| 有限水 | 水桶、积水、雨水、人工水池；可流走、渗透、蒸发 |
| 补给水 | 海洋、河流主干、泉眼；由水文状态有限补充 |
| 淡水 | 可直接饮用或简单净化 |
| 盐水 | 不应直接补水，可用于盐、蒸馏等后期内容 |
| 污染水 | 初期降低补水效率，后期可接入疾病或中毒 |

水格不应成为 Entity。初期可增加独立 `FluidLayer` 或 `FluidChunk` 保存水量、是否下落、盐度与水质；待通用方块状态系统成熟后再整合。流体使用 `ActiveFluidQueue`，仅处理放水、挖掘、降雨、融雪等事件影响到的格子，并对每个固定步设置预算。

### 7.3 季节与地形变化

低温时优先冻结表层、岸边和浅水；春季融雪进入地表径流、土壤和河流。远方只更新水文摘要，玩家附近才生成冰、水和洪水方块。侵蚀、泥沙与河岸变化应晚于稳定水文系统接入，并只修改明确属于自然地表的方块。

## 8. 植被、动态树与森林竞争

### 8.1 树的逻辑表示

树不应由每片叶子或每根树枝对应一个持续运行的 ECS Entity。逻辑树记录为根所在区块拥有的数据：

```text
TreeInstance
├─ root
├─ species
├─ seed
├─ stage
├─ age_days
├─ health
├─ last_simulated_tick
└─ next_update_tick
```

树干、枝叶和果实仍是普通体素方块。树形由 `species + seed + root + stage` 的确定性蓝图生成；存档保存逻辑状态、玩家修改和必要的异常，而不是保存每根程序化枝条。

### 8.2 生命阶段与季节状态

生命阶段与季节性表现必须分离：

```text
生命阶段：种子 -> 幼苗 -> 幼树 -> 成熟 -> 衰老 -> 死亡 -> 腐朽
季节状态：萌芽 / 盛叶 / 变色 / 落叶休眠
```

树在冬天落叶不等于死亡；死亡由年龄、持续干旱、根部破坏、病害或火灾等权威规则决定。

### 8.3 从细树到粗树的过渡

树干不应从 `1 x 1` 一次跳变为 `2 x 2` 或 `4 x 4`。树使用嵌套生长蓝图：后期蓝图必须包含早期蓝图，只追加新方块。

```text
幼树：1 x 1 树干
成树：底部 2 x 2，上部逐渐收成 1 x 1
古树：4 x 4 根基 -> 3 x 3 -> 2 x 2 -> 1 x 1 顶部
```

每次阶段转换生成 `GrowthPlan`：先增加根系和树基，再补低处树干、向上增粗、增加枝条，最后扩展树冠。计划按游戏日或生态间隔分批执行；每批只提交有限方块变更。偶数宽度树干没有与 `1 x 1` 完全相同的几何中心，因此种下时要记录稳定的扩张方向或基准角，保证后续生长不移动原树干。

空间不足时，树不得覆盖玩家建筑。它可以进入受限生长、延迟、停止、形成偏心树干，或选择较窄的替代蓝图。

### 8.4 树种定义与结构蓝图

新的内容定义可描述：

```text
TreeSpeciesDefinition
├─ 幼苗、树干、叶片、枯木、果实方块
├─ 生命周期与各阶段时长
├─ 温湿度、土壤、季节和光照要求
├─ 最大高度、冠幅、根系与枝条参数
├─ 耐旱、耐阴、耗水、固土和可燃性
├─ 种子、落叶、死亡和腐朽掉落
└─ 病害、火焰和恢复参数
```

当前静态结构生成器与运行时树苗生长共同调用纯 `TreeBlueprint`。世界生成和动态树生长共享树形算法，避免两套规则分叉。玩家种植的树苗成功生长后会创建由根区块唯一持有的 `TreeInstance`，其稳定树种标识、树形种子、成熟阶段、健康值和模拟时间会随区块保存。自然生成树的实例化以及幼树、衰老、死亡规则尚未接入。

### 8.5 森林竞争与远方摘要

动态森林必须竞争，但不能为整张地图上的每棵树持续计算。生态区块保存树冠覆盖、种子库、树种权重、年龄群体、土壤资源和扰动摘要。玩家附近或被修改的树才实例化为 `TreeInstance`。

竞争近似为：

```text
growth_score =
季节温湿度适宜度
x 土壤适宜度
x 可用空间
x 光照分数
x 水分分数
x 健康状态
```

树冠覆盖可使用区块内粗粒度网格近似，不需要对每棵树每帧追踪阴影。砍伐形成空隙后，光照与幼苗机会增加；干旱和去冠会提高侵蚀与退化风险。自然树位点应使用最小间距的稳定候选点，而不是每个地表列独立抽样，避免树冠过密和跨区块重叠。

## 9. 玩家生存、环境暴露与装备

核心生存状态建议保持有限且有因果关系：

```text
Vitals
├─ Health
├─ Energy / Hunger
├─ Hydration
├─ BodyTemperature
├─ Breath
└─ Stamina

Protection
├─ Armor
├─ Insulation
├─ Waterproofing
└─ RespiratoryProtection

Conditions
├─ Wetness
├─ Bleeding
├─ Poisoned
├─ Burning
├─ Hypothermia
├─ Heatstroke
└─ Exhausted
```

不要为所有状态永久显示数值条。生命、饥饿、口渴和护甲可常驻；体力在行动时显示；呼吸、严寒、过热、湿透、流血等只在风险出现时显示。

环境通过 `PlayerExposure` 统一采样后影响玩家：

```text
气候、天气、风、水、方块、地形
-> PlayerExposure
-> 装备、遮蔽物与热源减免
-> Vitals 与 Conditions 的固定步变化
-> Client 的 UI、音效、动画和视觉反馈
```

体温应是身体状态，而不是环境温度副本：

```text
体温变化 = 环境温度 + 阳光/篝火 - 风寒 - 湿衣散热
           + 食物代谢热 + 装备保温 + 遮蔽物效果
```

正常空气不应常驻显示氧气条；`Breath` 在水下、浓烟、毒气、密闭矿坑或后期高海拔环境中才成为危险。重甲也应有取舍：它能提高物理防护与部分保温，但降低体力恢复、游泳和炎热环境下的舒适度。

## 10. 庇护所、火、材料与建造意义

环境玩法必须给玩家明确的应对方式。最重要的闭环是：

```text
寒冷、降雨、大风
-> 湿冷、体温下降、行动受限
-> 寻找岩洞或搭建屋顶
-> 生火、烘干、取水、烹饪
-> 安全度过恶劣天气
```

初期不必模拟完整室内空气体积。`ShelterScore` 可由天空可见度、屋顶遮挡、周围墙体、开口、热源距离和风向近似计算。后期再扩展门窗、通风、烟雾与密闭空间。

火是连接系统的核心：

```text
火与热量
-> 保温、照明、烘干、烹饪、煮沸净水
-> 雨和湿木影响点燃
-> 风改变火势
-> 可燃植被导致局部火灾
-> 烟雾影响呼吸
```

材料不应只差硬度与纹理。长期应有可燃性、防水性、保温性、热容量、承重、透风性和腐朽速度等属性。木屋、石屋、泥屋和冰屋由此产生不同生存取舍。坍塌机制应极其克制，初期只用于自然洞穴、松散地层和明确危险区域，不应随意破坏玩家建筑。

## 11. 农业、食物、动物与生态位

### 11.1 土壤与农业

农业连接水、气候、树木和定居：

```text
降雨 / 灌溉 / 地下水 -> 土壤湿度
落叶 / 堆肥 / 植被 -> 肥力
温度 / 季节 / 日照 -> 生长速度
干旱 / 风暴 / 侵蚀 -> 减产与退化
```

第一版只需要水分、温度和肥力；轮作、病虫害、温室与复杂养分应后置。玩家应能通过水渠、蓄水池、堆肥、树篱和合适作物修复或利用环境。

### 11.2 食物保存与烹饪

食物系统应支持鲜食、熟食和保存食物，而不是一开始模拟维生素：

```text
采集 / 狩猎 / 种植
-> 食物会变质
-> 烹饪、盐渍、烟熏、发酵延长保存
-> 冬季、干旱与旅行形成储备压力
```

### 11.3 动物与生态位

远方动物使用种群摘要，玩家附近才生成具体实体。森林、草地、湿地和荒漠应拥有不同的食物链；动物可参与种子传播、授粉、啃食幼苗、捕食和资源供给。动物动态必须服从同样的距离分层和固定预算，不能因生态系统而持续生成大量实体。

## 12. 地下、地质与环境风险

地表与地下应形成不同的生存环境：

- 洞穴温度稳定，可作为避难所。
- 地下水、泉眼、矿洞积水与渗水。
- 烟雾、毒气、通风和局部呼吸风险。
- 菌类、苔藓、地下植物与稀有生态位。
- 地层、矿脉、化石、遗迹与旧河床。
- 受控的坍塌、松散岩层和危险区域。

地下氧气或毒气不应全局模拟每个空气方块。初期可使用区域级 `AirQuality` 与局部源头；只有矿坑、火灾、毒气穴等明确地点需要精细扩散。

## 13. 体素表现、Ray Traced Voxel 与 Micro Voxel

### 13.1 当前体素渲染的改进方向

区块网格系统应优先完善正确性和运行时边界：

- 统一体素修改入口，保证存档、邻居重建、光照和表现不会遗漏。
- 区块带修订号；后台网格输入与输出携带该版本，过期结果直接丢弃。
- 接入方块的 `Cube`、`Cross`、`Slab`、`Custom` 模型，处理遮挡、碰撞、选择与放置。
- 增加顶点环境光遮蔽、体素光照和水位几何后，将光照签名纳入贪心合并条件。
- 只在性能基线表明需要时引入 GPU 剔除、缓存池、压缩顶点或更复杂 LOD。

### 13.2 Ray Traced Voxel

推荐路线是混合渲染，而不是立即重写整个渲染器：

```text
Game 权威区块数据
-> Client 提取脏区块到 GpuVoxelWorld
-> DDA / Ray Marching 遍历体素
-> 阴影、AO、水面反射、一次间接光
-> 与现有贪心网格、实体、UI 合成
```

优先级：半分辨率首击调试 -> 太阳硬阴影 -> AO -> 水面反射 -> 发光方块与一次间接光 -> 摄影模式 Path Tracing。硬件 RT 接口应视为实验性可选路径，不能成为跨平台正式渲染的唯一依赖。

### 13.3 Micro Voxel

Micro Voxel 适合局部细节，而不适合将整张世界直接细分。全局把每个方块拆为 `8 x 8 x 8` 会将数据量放大 512 倍。

推荐结构：

```text
ChunkData
-> 普通方块 ID

MicroVoxelOverlay
-> 仅为被雕刻、破坏或特殊机器占用的方块存储 MicroBrick
```

可能玩法包括雕刻建造、局部破坏、地质与考古、积雪/泥土表面变化、细小机械和自然细节。射线遍历可先走宏观方块，再命中 MicroBrick 时进入局部网格。碰撞应使用合并后的简化形状，不能为每个小体素创建 Collider 或 Entity。

## 14. 世界修改、存档、确定性与玩家保护

所有改变方块的系统都应通过统一管线：

```text
VoxelChange
-> 修改权威区块数据
-> 增加 ChunkRevision
-> 标记中心和边界邻居
-> 标记存档脏数据
-> 触发光照、流体、生态和网格后续工作
-> 发出 Client 表现消息
```

树生长、流体、火灾、侵蚀、玩家挖掘和世界生成都应复用该管线。动态系统不能直接绕过它修改区块数组。

生态演化必须保护玩家作品。当前仅靠方块 ID 无法可靠区分自然沙地与玩家放置的沙地；在允许侵蚀、植被蔓延或表层替换前，应设计 `VoxelProvenance`、玩家修改位图或等价的持久化来源记录。任何存档格式变化必须增加版本、迁移路径和迁移测试。

随机事件只可通过确定性随机源生成，其输入包含世界种子、领域、生态/天气 Tick 和稳定位置键。不能使用本机真实时间或线程随机数决定权威结果。

## 15. 反馈、工具与可读性

复杂模拟必须向玩家提供信息与决策能力：

- 天空、云层、风声、雾、植被颜色和水位表现环境变化。
- 温度计、湿度计、风向标、雨量计、土壤检测与地下水探测提供精确信息。
- 地图可显示森林覆盖、干旱、洪水风险、已知流域与生态变化。
- 天气预报、日历和节气提示让玩家有准备时间。
- 火灾、旱灾、洪水和病害必须有预兆、缓冲与恢复手段，不能构成不可逆的随机惩罚。

Client 的风、叶片摆动、云、雨、雾、水面波纹和季节着色应主要是表现。季节到来时不应批量改写整片森林的叶子方块。

## 16. 分阶段实施路线

### 阶段 A：夯实权威世界边界

1. 完成权威世界数据、区块运行时状态和 Client 表现资源的职责迁移。
2. 建立 `VoxelChange`、`ChunkRevision` 和过期网格结果丢弃。
3. 为新增持久化字段建立格式版本与迁移测试。
4. 维持现有性能基线，先测量再优化。

### 阶段 B：第一个可玩的环境纵切面

```text
降雨和降温
-> 玩家湿冷、口渴和体温压力
-> 屋顶、篝火、取水、烹饪
-> 雨水进入土壤
-> 附近树木和作物获得水分
```

该阶段接入玩家暴露、湿润度、简单淡水、基础庇护和火，不要求完整流体或全球天气。

### 阶段 C：生态与定居

1. `EcologyPatch` 的土壤水分、肥力、树冠和动态土地覆盖。
2. 玩家种植的树：幼苗、离散成长、受限空间、存档和季节休眠。
3. 作物、灌溉、堆肥和基础食物保存。
4. 自然森林从静态结构逐步升级为摘要与近距离实例化。

### 阶段 D：水文与天气

1. 粗粒度天气单元、降雨、干旱、风力和蒸发。
2. 活动区块中的有限水量、渗透、积水和局部水渠。
3. 种子水文骨架、泉眼、季节河流、地下水与融雪。
4. 冻结、洪水、局部侵蚀与水生生态。

### 阶段 E：高级世界表现与长期内容

1. 体素光照、AO、改进水面和方块模型。
2. 混合 Ray Traced Voxel 表现。
3. 局部 Micro Voxel、雕刻和细粒度破坏。
4. 火灾、病害、动物生态、风暴、地质风险与遗迹历史。
5. 风车、水车、运输、定居地和更复杂的玩家环境治理。

## 17. 验证与测试要求

每个系统应附带确定性、边界和存档测试：

- 相同世界种子、命令流和模拟 Tick 必须产生相同生态状态。
- 不同渲染帧率不能改变树木年龄、水量、天气事件和玩家生存结果。
- 未加载区块的补算与连续加载模拟在定义允许的误差范围内一致。
- 玩家放置方块不会被生态、侵蚀或树木生长覆盖。
- 跨区块树、水、光照和结构修改不会遗漏邻居更新。
- 过期后台网格或生成结果不能覆盖新版本区块。
- 存档升级后，旧世界的生成版本、区块 ID 重映射和生态状态保持可读。
- 内容定义的树种、材料、作物和生态规则都通过内容校验。

大型场景应使用固定的性能基线：固定种子、固定渲染距离、固定相机状态、固定采样窗口。优化必须说明改善了哪一项指标，不能只凭主观帧率感觉。

## 18. 设计取舍与待决问题

以下选择会影响大量后续实现，应在进入对应阶段前明确：

1. 水是完全有限资源，还是河流、泉眼和海洋拥有有限补给速率的再生资源？
2. 世界时间是否只在游戏运行时推进，离线时是否进行生态补算？
3. 动态生态的最小空间尺度是 64、128 还是更大的方块区域？
4. 树木、动物和作物的“远方摘要”需要多强的精确性，哪些玩家影响必须永久保留？
5. 火灾、洪水、坍塌是否允许损坏玩家建筑；若允许，玩家有哪些预警、缓解和恢复工具？
6. 生存系统的困难度如何与创造模式、辅助模式和未来多人模式分层？
7. 动态地表替换如何识别玩家建造并保持存档兼容？
8. Ray Traced Voxel 与 Micro Voxel 是可选画质路径、摄影模式功能，还是核心玩法依赖？

在这些问题没有答案前，不应以“先实现再说”的方式让多个系统直接耦合。优先完成一个小而闭合、可测试、可恢复的环境纵切面，再向外扩展。
